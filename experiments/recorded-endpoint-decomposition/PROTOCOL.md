## Decision this audit can settle

This one-off exploratory secondary analysis asks whether any recorded two-PLACE endpoint offers a better value of the existing H geometric component than every comparable collection-containing endpoint, while leaving more equipment uncollected. It can distinguish that fixed-component tradeoff from componentwise domination of two-PLACE endpoints on this already-spent population. It cannot decide which action is strategically better, validate the geometric component, estimate a win rate, or establish that preserving a card helps future play.

The unchanged-H/horizon-two strict-departure advancement line is already closed by the PR #36 acceptance. This explanatory audit is optional and is not a prerequisite for that closure. It does not automatically advance a policy, enlarge a horizon, open a parameter search, change H, allocate seeds, or reopen the closed Worker31 candidate.

## Exact equipment and EXIT bookkeeping

For each recorded sequence, start with the original hand-index list and the snapshot's exact-integer counts `r0` and `p0`, with `0 <= r0 <= 3` and `0 <= p0 <= 2`. Initialize `x` from the snapshot's exact-Boolean `exit_placed`, not from hand contents or a default. For every numeric field described as an integer in this protocol, JSON true/false, floats and numeric strings are invalid substitutes.

Require every original hand card to have a nonempty string `card_id`, unique within that original hand; `material` must be exactly null, `raincoat` or `rope`; and `is_exit` must be an exact Boolean. An EXIT card must have null material. Allow at most one EXIT in the original hand, and reject a hand containing EXIT when the initial `exit_placed` is already true. The inert public snapshot and card definitions must retain the exact original source schema; these checks interpret only the fields necessary for bookkeeping, not their geometry.

Every recorded action object must contain exactly the keys `action`, `hand_index`, `origin` and `quarter_turns`, with no omitted or extra keys. `action` must be exactly the string `collect` or `place`. `hand_index` and `quarter_turns` must be exact integers. A COLLECT action requires `origin: null` and `quarter_turns: 0`. A PLACE action requires an origin array of exactly two exact integers and `quarter_turns` in 0 through 3 inclusive. These are recorded-wire validation checks, not a geometric legality test.

Process only the already-recorded sequence metadata in order:

1. Resolve its index against the current original-card-ID list and remove that ID. Reject a noninteger index, Boolean-as-integer, out-of-range index, repeated physical-card use or malformed action.
2. For COLLECT, require a raincoat or rope card and require that material's current count to be below its exact quota before incrementing only that coordinate. Collection of an EXIT or material-free card is invalid. No decrement or quota excess is allowed.
3. For PLACE, leave both equipment coordinates unchanged. Set the endpoint EXIT flag to true if the selected original hand card is marked EXIT; otherwise preserve it. Reject incompatible metadata such as an already-placed EXIT also present for a new EXIT placement.
4. Validate original hand card identities and their material/EXIT metadata against the pinned public snapshot. No new card is appended and no hand refresh is inferred.

This produces endpoint `(r, p, x)` solely from fixed public inventory and recorded actions. Raincoats and ropes remain separate coordinates; three raincoats are not treated as interchangeable with three ropes, and a total equipment count is not used for quota readiness or dominance. Componentwise larger counts within these exact quotas represent more acquired requirements only. They do not imply a better complete game state because card geometry has been consumed.

Define the equipment term `I = 10000 * (r + p)` solely to remove the exact term used by frozen H.

Define the frozen endpoint EXIT term:

- `X = 0` when `x` is false
- `X = 5000` when `x` is true and `(r, p) == (3, 2)`
- `X = -5000` when `x` is true and the exact quotas are not both met

Use readiness at the endpoint. Do not use readiness at the moment EXIT was placed or apply V4's separate action-reward convention. For an eligible nonterminal leaf, take the already-recorded integer `h = key[2]` and derive `G = h - I - X`.

No engine H evaluation is performed. G is an algebraic decomposition of recorded H and, conditional on the already-accepted Worker33 semantics, represents its existing weighted geometric component:

`-100 * open_tunnels - 20000 * visible_water_cells - 1000 * water_obstruction - 100000 * trapped_water_cells + 250 * bounded_merge_bank`

The bounded merge bank is the existing source definition, zero when open tunnels exceed 10 and otherwise `min(merge_opportunities, 6)`. These features are not recalculated. G is one common integer score for the audit, not a new evaluator, a featurewise geometry dominance proof, or a validated measure of future success. No division, fitted coefficient, rounding, tolerance, normalized score or weight sweep is allowed.

## EXIT stratification and exact dominance relation

EXIT placement is required for victory, but its placement can change board geometry and future options. Existing evidence does not prove that EXIT placed is monotonically better at every nonterminal endpoint. The audit therefore does not put EXIT on a monotone preference axis.

Compare endpoints only within the same observation, key/reason class, sequence depth and exact endpoint EXIT flag `x`. In the primary analysis, depth is always two and key/reason class is always nonterminal horizon. EXIT-false and EXIT-true endpoints are separate strata; there is no cross-EXIT comparison.

Within one such stratum, endpoint a component-dominates endpoint b if and only if:

- `r_a >= r_b`
- `p_a >= p_b`
- `G_a >= G_b`
- At least one of these three inequalities is strict

All comparisons use exact integers. Equal `(r, p, G)` vectors are ties and do not dominate each other. Duplicate vectors remain represented in the output and receive the same comparison result.

For a collection-containing endpoint versus PP from the same observation, the former necessarily has a strict increase in at least one equipment coordinate and no equipment decrease. Consequently equal G is sufficient for component-domination of PP. This special case must follow from validated metadata rather than be assumed from the label alone.

The term component-domination is deliberately narrow. It excludes retained-hand contents, placement history, timing, future draws and every geometric distinction not represented by G. It must not be shortened in the report to “the action is dominated” or “collection is optimal.”
